# 统计批量查询优化验收记录

状态：本轮实现、WSL 单元/race 检查和 Windows 实际 WebView 验证完成。没有新增持久索引、Goose SQL 或版本号变化；Linux 实际桌面仍需验证。

## 定位结果

此前统计页的“逐日统计请求”约 1.6 秒并非一条 SQL 的耗时。一个月发起约 30 次 Binding 请求，每次在单连接下重新计算全表本地日期，原始 SQL 中的休息累计还会回查历史记录。

测试编译 overlay 对 API 总时间、等待生命周期锁时间、SQL 遍历/映射时间分别记录。原查询的 101 次采样中，SQL 中位数约 53.6 ms，含 JSON 编码的工作时间约 54.0 ms。月请求按顺序等待，最后一个请求可等待约 1.5 秒；双周期切换重叠时等待更长，不能把重叠的等待时间相加解释为 SQL 总耗时。

前端实测含学习记录响应的 JSON 解析合计中位数约 0.2 ms，主要开销在重复 SQL 和排队。优化后一个月的 SQL、遍历与映射约 63 ms，API 总时间约 65 ms；前端查询阶段中位数约 71 ms。计时只在测试 overlay 中详细打印，产品没有加入每次查询的诊断日志或调试端口。

原始记录见 profile/、profile-after/，其中测试数据全部独立生成。

## 实现与数据规则

- 新增 `GET sessions/batch?date=YYYY-MM-DD&date=YYYY-MM-DD`，返回 `日期 -> Session[]`，重复日期去重，无记录日期保留空数组；无日期返回空对象。
- 单次最多接收 62 个日期，覆盖两个自然月，避免无界批量请求；非法日期和非 GET 请求返回错误。
- 原单日接口仍返回数组，空日期仍使用今天，非法单日日期仍保持空数组行为。
- 统计页整页加载、趋势周期切换和概览周期切换都使用批量入口；趋势/概览重叠日期仍只加载一次。
- 日期继续由 SQLite `date(start_at,'localtime')` 计算，没有按字符串前十位截取，没有假设数据库时间统一为 UTC。
- 查询先将请求日期的记录物化为本次 SQL 的临时结果集，再从该结果集计算休息累计，避免每条记录反复扫描整个历史库。
- 软删除记录在最终输出时才过滤，保留它们对同一计划、同一自然日历史休息累计的贡献；累计条件仍为较小 id，与时间排序无关。
- NULL 计划只返回本条休息用量；计划 id 为 0 时仍按原有非 NULL 计划规则累计。
- 返回字段、可空时间、原始时间字符串、时长单位、记录来源及排序保持不变。进行中记录继续交给原有前端计时规则实时计算。
- 保持单连接与 `WithAccess` 生命周期借用；这是只读查询，没有新增连接、事务管理或跨请求缓存。临时结果集不写入主库，不属于新增持久索引或结构升级。

## Windows 前后对照

对照版为此前已完成的启动/内存优化版本，候选版仅增加本轮查询优化；并非再次与最初 HEAD 比较。两版均以相同生产优化参数编译，只通过测试 overlay 开启调试端口并隔离配置/浏览器缓存。二进制校验见 binary-sha256.json。

主要数据集为 365 天、每天 24 条，共 8760 条手动记录。三次启动、每次三次统计加载/刷新，两版完整记录哈希和图表数值全部一致。下表取中位数。

| 指标 | 修改前 | 修改后 |
| --- | ---: | ---: |
| 逐日/批量统计请求 | 1637.3 ms | 70.6 ms |
| 整次月刷新（9 次） | 1734.3 ms | 186.9 ms |
| 每轮第一次月刷新（3 次） | 1734.3 ms | 341.4 ms |
| 首次进入统计页 | 881.3 ms | 423.8 ms |
| 再次进入月统计 | 1771.9 ms | 216.3 ms |
| 含记录响应的 JSON 解析合计 | 约 0.2 ms | 约 0.2 ms |

整次刷新中位数约缩短 89%，首次月刷新仍有约 0.34 秒，不能宣传每次都只需 0.19 秒。图表就绪不代表其后续动画全部结束；这些也是单机小样本观测，不是所有设备的保证。

## 内存核对

本轮没有扩大长期缓存。快速连续刷新后立即采样时，总私有内存在部分候选版样本中更高，因此另做了分进程检查，在离页后再等待 5 秒采样：

| 轮次 | 修改前总私有内存 | 修改后总私有内存 | 修改前 Go 主进程 | 修改后 Go 主进程 |
| --- | ---: | ---: | ---: | ---: |
| 1 | 394.6 MiB | 384.0 MiB | 66.9 MiB | 64.9 MiB |
| 2 | 391.4 MiB | 413.3 MiB | 65.7 MiB | 65.6 MiB |

Go 主进程没有出现明显的持续增加，总量仍受 GPU/渲染器等进程波动影响。三轮对照离页后 JS 堆约为 8.54 -> 8.55 MiB。这里不能宣称整体内存下降，也不能把某一次即时快刷取样当成稳定增加量；本轮没有连续监测完整峰值或进行数小时驻留验收。

内存采样范围包含本次应用的整个进程树，JS 堆经显式 GC 后采样，仅用于对比保留量，产品没有增加强制 GC。原始分进程记录见 memory-settled/。

## 复现实验

沿用 scripts/qa/prepare-startup-memory.py 和 test-startup-memory-windows.mjs，准备带测试端口和隔离路径的两份 Windows 二进制后运行：

```sh
python3 scripts/qa/prepare-startup-memory.py \
  --before-binary /path/to/before/StudyFlow.exe \
  --after-binary /path/to/after/StudyFlow.exe \
  --record-mode manual --history-days 365 \
  --temp-dir /mnt/c/Users/USER/AppData/Local/Temp
mkdir -p OUTPUT
QA_QUERY_PROFILE=1 node scripts/qa/test-startup-memory-windows.mjs FIXTURE_ROOT OUTPUT
```

`--record-mode mixed/planned` 生成其他场景；QA_RUNS、QA_CYCLES 控制次数；QA_VARIANTS=after QA_FEATURES=1 执行候选版补充功能；QA_MEMORY_SETTLE_MS=5000 进行稳定后取样。不要并行运行使用同一调试端口的窗口实验。

当前仍会进行一次全库日期筛选；规模继续增长时需重新测量，不能推断十倍数据仍有相同延迟。索引暂不需要；若以后确有必要新增持久索引，仍须按 AGENTS.md 11.1 取得 Goose 增量 SQL 的明确授权。
