# 数据库跨版本兼容、升级与回退设计

日期：2026-11-18。状态：设计草案，尚未实现。本设计先于数据库导入导出功能落地。

## 1. 目标和边界

升级成功后，新版本使用经过验证的数据；升级失败或被中断时，能够确定正在使用哪一份数据库并恢复。回退必须明确能否保留新版期间的数据，不静默丢失数据、不自动猜测数据库版本、不强行删除字段降级。

本期实现数据库兼容检查、升级和恢复到旧版可用状态的能力。应用安装包的下载、安装、覆盖正在运行的可执行文件及操作系统包管理器降级不纳入本期。回退界面完成数据库准备后退出，用户启动对应旧版；后续可接入安装器，不能把数据库恢复成功等同于程序版本回退成功。

无法让已经发布且没有版本检查逻辑的旧程序自动遵守新协议。对这些程序仅提供已验证历史格式的快照恢复路径，不承诺其直接打开新版数据库安全。所有后续版本都必须使用统一兼容入口。

不保证硬件损坏、用户手工删除所有恢复副本、文件系统虚假报告持久化成功时仍能恢复。正常错误、文件占用、空间不足、进程退出与受支持本地文件系统上的崩溃恢复必须覆盖。网络共享及跨操作系统同时使用同一活动库不属于首期支持范围。

## 2. 当前代码基线

- `desktop/startup_database.go` 负责选库、位置切换恢复、启动打开和句柄接管。
- `persistence.OpenForStartup` 当前执行 quick_check、有限结构校验、原地逐条初始化/迁移及再次校验。
- 历史五表结构有三种完整匹配；现代结构主要检查必要列可查询，缺少完整约束及既有外键违规检查。
- 没有应用使用的数据库格式编号、迁移账本、未来版本拒绝机制，也没有原子迁移保证。
- 初始化会转换目标验收状态、软删除历史短手动记录及调整旧颜色；不能继续每次启动重复执行这些业务转换。
- `Database.Replace`、在线快照和数据目录切换已有生命周期锁、文件身份及恢复协议，可复用底层能力；现有目录迁移有删除旧文件的语义，不能直接用于要求保留旧库的版本升级。
- Windows 单实例锁按应用名，Linux 按 baseDir；均不能代替实际数据目录的维护锁。

## 3. 版本模型

应用版本与数据库版本独立。界面、样式等改动不增加数据库版本；表结构、约束、枚举含义、历史记录解释或持久化业务规则发生不兼容变化时，必须增加数据库版本。

使用一个递增整数 `format_version` 同时描述结构和持久化数据语义，避免出现“列相同就误认为可互写”。首个纳管后的当前结构为版本 1，后续为 2、3……。已有无编号结构使用历史 profile 标识，不把所有无编号数据库统称为版本 0。

数据库增加：

| 元信息 | 用途 |
| --- | --- |
| `PRAGMA application_id` | 固定 StudyFlow 标识；非零且不匹配则拒绝 |
| `PRAGMA user_version` | 格式编号，必须与元信息一致 |
| `studyflow_meta` 单行表 | 元信息协议版本、database_id、generation_id、format_version、创建/最近迁移应用 build_id、UTC 时间 |
| `studyflow_migrations` | 已完成迁移 ID、from/to、迁移校验摘要、执行 build_id 和完成时间 |

database_id 标识逻辑数据库谱系；generation_id 在升级/恢复生成新副本时更新，用于判定文件切换结果，不冒充学习记录版本号。build_id 为构建时嵌入的不可变发布标识，不能从文件名猜测。现有 9 张业务表继续保留，新增 2 张管理表；将来完整数据库导出应包含它们。

build_id 至少包含应用版本和实际构建源码摘要；只有 Git commit 不足以区分含未提交修改的日常构建。构建产物嵌入兼容声明，以同一机器可读格式供恢复界面核验；历史构建没有声明时只能依据已验证的发布档案/profile，不假装从旧程序中读取到了声明。

每个程序编译时声明：自身 build_id、唯一可写格式、可识别历史 profiles、升级路径、元信息协议版本和该格式的结构/数据规则。首期不实现跨格式写入，也不提供功能不完整的只读主界面。

版本记录与校验摘要用于发现错误及不一致，不是数字签名或不受篡改的证明。SQLite 自身 schema_version 不是应用兼容版本，不能用它替代 format_version。

## 4. 启动判定

在初始化业务服务、定时任务、自动备份和任何数据修复之前执行；错误时进入独立恢复界面，不先打开正常主页。

| 输入 | 行为 |
| --- | --- |
| 确认真正首次启动且不存在待恢复操作 | 创建最新格式 |
| 同格式，元信息、结构、数据校验一致 | 正常打开，不执行历史转换 |
| 已知旧格式，升级链完整 | 展示升级计划和备份位置，确认后在副本升级 |
| 格式高于程序支持范围 | 拒绝读写；显示所需格式、当前支持格式和最近迁移 build_id |
| 无编号且完整匹配已知历史 profile | 展示纳管升级计划，先留原样快照再转换 |
| 未知无编号结构、版本记录矛盾、迁移账本异常 | 拒绝推断和自动修补，保留原库并提供诊断 |
| 文件丢失、损坏或上次维护未完成 | 先恢复/报错，不用空库替代 |

拒绝兼容性时，不执行建表、补字段、设置默认值、清理历史数据或后台备份清理。不做会在源库上创建 sidecar 的写入式试探；检查在合适的只读连接或一致性快照中进行。不得用 immutable 模式忽略仍有有效 WAL 的数据库。

全部生产入口统一调用 CompatibilityManager，包括正常启动、位置切换恢复、旧位置迁入和未来导入；原 `Open` 拆分为明确的“新建”“已验证打开”“迁移候选打开”，避免通用初始化函数绕过版本保护。

## 5. 历史 profile 与迁移

先收集当前已支持的三种五表 fixtures、八表阶段、阶段目标未含 accepted_at 阶段，以及实际发布过且可取得的数据库结构。每种 profile 整体匹配列、类型、主键、唯一性、非空、默认值、外键、已知索引/触发器及关键值范围。只声明已由 fixture 和测试验证的支持范围；部分混合结构不能推断成某个旧版。

识别结果不依赖目录名、文件名或仅凭列数；无法识别的文件保持原样。当前现代校验接受过的额外未知对象不能自动当成合法版本。

迁移注册为确定的 `from -> to` 单向步骤，有稳定 ID、校验摘要、前置条件和后置校验。已完成步骤不重跑，升级链不能跳号。DDL、数据转换、账本及版本号更新在同一候选库事务中提交；不允许混入需脱离事务的 VACUUM、系统设置、网络或外部文件副作用。

首次纳管特别处理：

- 无 accepted_at 的旧目标，按已知规则将 completed_at 转成已验收；已有 accepted_at 的结构不能重新套用同一推断。
- 历史不足 600 秒手动记录的处理是业务兼容转换，预览列出受影响数量；不物理删除原始行，原样快照仍保留。
- 颜色转换只在明确 profile 的迁移中执行一次，不能每次启动根据颜色值重新判断历史来源。
- 无时区历史时间戳不能随意按当前机器时区改写；原文保留并记录 profile 的解释规则。不能确认解释方式时停止自动转换并说明问题。

已有记录已经被当前代码转换的，不能根据现有值猜测转换前状态；不承诺首次纳管能恢复已丢失的历史语义。

## 6. 校验范围

升级前验证来源，升级后及正常兼容启动验证目标；昂贵的全量校验至少在迁移、恢复和导入时执行，日常启动校验成本按数据量评估。

- SQLite integrity_check（维护时）、quick_check（日常启动）和 foreign_key_check。
- 按格式的结构清单核验类型、主键、唯一、非空、默认值、外键、索引及程序拥有的触发器；不从未知库中执行任意修复 SQL。
- 标准 SQLite 元对象按其规则处理，不能把 sqlite_sequence 等一概判成未知业务表。
- 关系补查：例如 sessions.plan_id、追因明细等没有完整 SQL 外键约束的关联，考虑软删除与已知历史快照规则，不机械拒绝合法历史记录。
- 数据校验：日期/带时区时间戳、JSON 结构、布尔/枚举、时长、排序值、设置范围；每个规则绑定格式和 profile。
- 迁移前后按步骤核对记录数、ID/关联以及应保持不变的关键字段；预期变化单独统计，不能只比较总行数。

## 7. 升级流程

1. 选定真实数据目录；恢复现有目录切换协议后再开始版本维护，两种维护操作不能重叠。
2. 获取实际数据目录维护锁和应用实例锁，确认没有本应用的活动计时/未提交编辑。升级启动阶段不运行提醒及统计更新。维护锁需防止其他遵守协议的安装目录同时打开同一个数据目录。
3. 检查兼容性并展示升级计划。已知库中的未结束计时记录须先通过受支持恢复流程处理；不把离线时间自动计入学习时长，也不在用户确认前修改原库。
4. 检查空间与权限。通过 SQLite 快照生成不可变的升级前备份，并验证它；然后由该备份生成独立候选库。失败则不迁移。
5. 在候选库执行完整迁移事务，做结构、数据、关联及应用查询的无副作用就绪验证；失败丢弃候选资格，继续保留原库和备份。
6. 刷新候选库和备份，持久化维护记录。暂停并排空所有数据库使用，处理 WAL/checkpoint；关闭所有参与切换的 SQLite 连接，确保候选是完整独立主文件。
7. 在当前数据目录内发布候选库，使用平台文件操作和持久化操作记录协调保留旧文件、发布候选。Windows 不在打开的 SQLite 句柄上覆盖文件；Linux 也不允许旧连接继续向被重命名的旧库写入。
8. 从 study.db 重新打开并核验 generation_id、格式和就绪查询。持久化提交状态后才允许业务请求、提醒及后台任务写入。
9. 标记完成。原样升级前备份持续保留；仅可清理本次确认归属的临时候选，不自动删除用户文件。

维护流程不能以“SQLite 正在使用，删除 WAL/SHM 再试”作为恢复手段。保留主库及其仍有效的 sidecar 整体，由 SQLite/明确的恢复流程处理。在线快照必须包含所有已提交 WAL 内容。

## 8. 文件布局与崩溃恢复

在当前数据目录保存维护记录和同文件系统候选；备份放在 `backups/compatibility-<operation-id>.db`，配套 `compatibility-<operation-id>.json` 记录来源 profile/format、build_id、时间、文件摘要、数量概要及关联操作。命名与现有 `study-时间.db` 轮转分开，升级/回退备份不按两天自动删除。

恢复协议使用版本化记录，含 operation_id、kind、phase、数据库谱系/代次、旧库/候选/备份相对路径、文件身份及准备时摘要。仅接受该数据目录中可验证归属的路径，拒绝越界、符号链接替换和未知操作协议版本。摘要不是文件替换授权的唯一依据。

阶段为 preparing -> prepared -> switching -> published -> committed -> completed。阶段记录本身不是唯一真相，要结合实际文件身份、generation_id、SQLite 校验及提交标记结算。准备与提交边界均有文件刷新；Linux 目录 fsync 与 Windows 发布/刷新语义分别实现并测试，不把多次 rename 说成单次原子操作。

| 中断位置 | 下次启动处理 |
| --- | --- |
| 备份/迁移未完成，原库仍有效 | 保留原库，识别并隔离本次未完成候选，可重试 |
| 候选就绪但未发布 | 原库继续有效；可重试发布或取消 |
| study.db 暂时缺失，旧库/候选均在 | 根据已验证记录完成发布或恢复原库，禁止新建空库 |
| 已发布、尚未提交，业务写入尚未允许 | 验证候选并完成提交，或恢复已验证旧库 |
| 已提交，完成标记未清理 | 使用已提交代次，不能回退并丢失提交后的业务写入 |
| 身份、元信息或文件内容矛盾 | 停止写入并保留全部证据，要求选择恢复方案 |

不能确定结果时拒绝继续，不能按“修改时间较新”选库。已提交库发生损坏也不能悄悄恢复旧快照，因为可能丢失升级后的学习记录。

备份清理、修改数据目录和未来导入都必须尊重维护状态。数据目录迁移需连同兼容备份及清单一起迁移，相对路径重新验证；维护未结算时禁止迁移目录。

## 9. 回退策略

### A. 同格式保留数据回退

仅当目标程序属于兼容机制纳管版本、编译声明能写当前 format_version，且该源/目标 build 的回退组合已验证，允许保持当前数据库。先保留当前快照，检查设置及业务规则兼容，再正常退出并交给旧程序。

同格式不是仅仅表结构相同。持久化规则的变化若不满足互写要求，开发阶段必须增加格式版本；针对补丁版本也要运行回退测试。

### B. 格式不兼容时恢复快照

目标格式较旧，不执行通用反向迁移。查找该升级链上实际保存、且目标程序可读取的升级前快照；多次升级可选择相应检查点。没有合适快照则拒绝一键回退，不能虚构旧字段或自动删除新功能数据。

预览展示目标程序/profile、恢复检查点时间、各类数据数量差异，以及“检查点之后的记录不会出现在旧版中”。先把当前完整数据库保存为独立回退前快照并验证，用户确认后，复制旧快照为候选，再使用与升级相同的文件发布/恢复协议。原旧快照和新版回退前快照都保持不可变。

两份快照不是自动合并承诺：将来再次使用新版，可选择恢复回退前新版快照，或者升级旧版期间继续积累的数据；首期不合并两条分叉历史，界面必须说明。

恢复到未纳管历史程序时，候选保持历史结构原样，不为写入 generation_id 而添加管理表。此时发布恢复依据外部操作记录、文件身份、profile 与准备时摘要；不能要求历史库具有新版元信息。快照还原只恢复数据库，不恢复旧版安装包、系统自启动或本机文件。

### C. 程序交接与防止立即重升

维护记录另存 rollback_handoff，记录目标 build/profile、恢复代次和交接状态。完成数据库准备后退出。具备本协议的新程序若发现目标不是自身，不得直接把刚恢复的库再次升级；提供“启动对应旧版”说明和“取消回退，恢复回退前快照”操作。

纳管目标程序成功校验并接管恢复库后确认交接。对于没有协议的历史程序，无法自动确认交接，也不能阻止用户绕过入口手动启动它；首次重新打开纳管程序时显示未确认的历史回退状态，由用户选择继续升级当前旧库或恢复新版快照，不能自动覆盖旧版期间新增记录。

build_id 必须读取受支持程序的实际声明，不能只相信用户选择的文件名。初期不自动运行任意所选可执行文件，也不伪装已完成软件降级。

## 10. 跨平台规则

格式编号、DDL、迁移和数据校验规则在 Linux/Windows 共用；文件锁、文件身份、持久化发布与恢复由平台适配。当前 Linux 目录通常在 ~/.StudyFlow，Windows 默认在程序旁；所有维护产物跟随实际选定的数据目录。

数据库设置可迁移，系统自启动、窗口位置和数据目录不由数据库恢复覆盖；内置铃声由程序生成。日期字段保持自然日，历史时间戳保留原值和偏移，计划时钟按目标机器本地时区执行。历史按 localtime 聚合的统计跨时区可能改变归属，这是现有业务规则，不能承诺与操作系统无关的跨时区统计完全相同。

维护锁只约束遵守协议的程序；历史程序和外部 SQLite 工具可能绕过它。维护前必须排除其他写入者，切换时通过 SQLite 锁及文件占用检查尽力确认，不能宣称能阻止任意不合作的外部进程。

## 11. 用户界面

正常同格式启动不新增弹窗。需要迁移时显示来源/目标格式、数据概况、会改变状态的记录数量、升级前备份位置，以及“升级并打开”和“退出”。失败显示已确定的状态、保留文件和可操作的恢复选项。

设置页提供“版本与恢复”入口，放置在数据库维护相关区域。显示当前应用/数据库版本、升级检查点，以及“准备版本回退”；自动备份开关、数据目录和未来导入导出的具体页面布局另行实现。

回退选择目标与检查点后再预览。若同格式可保留最新数据，明确展示；若需恢复检查点，明确展示恢复时间和差异，再确认。当前有计时、编辑、备份或目录切换任务时不能直接替换数据库，提供结束/保存后再试的具体说明。

## 12. 实施拆分与验收

1. 先实现只读结构识别、格式元信息、统一入口和未来格式拒绝；补齐现有校验缺口，建立 fixtures。该阶段不擅自把用户库标为已纳管。
2. 实现目录维护锁、保留快照、候选事务迁移、文件发布协议和故障恢复，再接入一次性历史纳管。
3. 实现回退检查点、差异预览、交接状态和取消回退。复用同一维护协议，不新增第二套随意复制数据库的路径。
4. 通过 Linux/Windows 验收后才接数据库导入导出；导入应调用本机制的识别、候选升级及发布能力。

必须通过的测试：

- 每个已声明历史 profile -> 当前格式，连续多步升级、重复启动不重复转换；升级失败原库逐项保持不变。
- 同格式不同 build 保留记录回退；不兼容格式拒绝直接打开；有/无旧快照的回退；回退后旧版新增记录再升级；两条数据历史不自动合并。
- 未知未来编号、伪造/冲突元信息、错误字段类型/约束、既有孤立关联、异常日期/JSON/设置、未知对象和缺失迁移账本。
- 迁移中途 SQL 错误、磁盘满、权限拒绝、备份校验失败、WAL 中有已提交内容、存在未结束计时和未保存编辑。
- 各持久化阶段用子进程中断后重启，包括发布前后、提交前后；不能依赖同进程模拟返回错误替代真实中断测试。
- Windows 本地 NTFS 实际运行与 Linux 本地文件系统实际运行；跨平台数据库双向校验；不同程序目录指向同库的并发维护。
- 迁移/回退备份不被自动轮转删除，目录迁移完整带走兼容检查点，源文件/符号链接被替换时停止操作。

交付标准是已声明支持范围内的升级、失败恢复和回退均有自动化与平台实测依据；不能用“SQLite 能打开”或“页面正常显示”替代数据正确性验收。开发和测试不更改固定测试版本号、不初始化或清空用户数据库，实际用户库纳管前须先完成备份与验证。
